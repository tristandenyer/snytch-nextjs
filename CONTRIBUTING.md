# Contributing to @snytch/nextjs

Thank you for your interest in contributing. This document walks you through everything you need to go from first clone to a ready-to-review pull request. It assumes no prior familiarity with this codebase.

---

## Before you start

Check the [open issues](https://github.com/tristandenyer/snytch-nextjs/issues) before writing any code. Someone may already be working on the same thing, or there may be context that changes your approach.

For large features or significant changes to existing behavior, open an issue first to discuss the approach. A quick conversation upfront avoids a situation where you spend time on an implementation that goes in a different direction than expected.

For small bug fixes, typo corrections, and documentation improvements, a pull request without a prior issue is fine.

---

## Prerequisites

- Node.js 18 or later
- npm (comes with Node.js)
- git

---

## Fork and clone

1. Fork the repository on GitHub.
2. Clone your fork:

```bash
git clone https://github.com/<your-username>/snytch-nextjs.git
cd snytch-nextjs
```

3. Install dependencies:

```bash
npm install
```

4. Confirm the test suite passes before making any changes:

```bash
npm test
```

---

## Project layout

```
src/                  TypeScript source files
src/commands/         One file per CLI sub-command (scan, check, diff, demo, mcp)
src/tests/            Vitest test files — named <module>.test.ts
dist/                 Compiled output — never edit manually
```

The entry point for the CLI is `src/cli.ts`. Each sub-command is wired up there and implemented in `src/commands/`. Core logic (pattern matching, scanning, output formatting, report generation) lives directly in `src/`.

---

## Making changes

- Edit files in `src/`, never in `dist/`. The `dist/` directory is generated by `tsc` and overwritten on every build.
- All relative imports must use `.js` extensions, even when importing `.ts` source files. This is an ESM requirement:
  - Correct: `import { foo } from './utils.js';`
  - Wrong: `import { foo } from './utils';`
- All exported functions, types, and interfaces must have JSDoc comments with `@param` and `@returns` (and `@throws` if applicable).
- No `any` type. Use `unknown` and narrow it. No `@ts-ignore` without a comment explaining exactly why.
- No `process.exit` outside `src/cli.ts`.
- Secret values must never appear in full in any output, test fixture, or report. Use `truncateValue()` for display.

See [CLAUDE.md](CLAUDE.md) for the full set of rules the project follows.

## Running tests

```bash
npm test               # Run the full Vitest test suite
npm run typecheck      # TypeScript type checking (tsc --noEmit)
npm run lint           # ESLint + Prettier
npm run build          # Compile TypeScript to dist/
```

Tests live in `src/tests/`. Each test file is named after the module it covers: `src/tests/scan.test.ts` tests `src/scan.ts`, and so on.

Use `vi.mock` for all filesystem and process I/O. Tests must never touch the real filesystem or make network calls.

---

## Validation checklist

Run these four steps in order before opening a pull request. Do not skip any step. Do not open a PR if any step fails.

```bash
npm run lint
npm run typecheck
npm test
npm pack --dry-run
```

The `npm pack --dry-run` step verifies that only `dist/` and `README.md` are included in the published package. If you see any other files in the output (source files, test files, config files), check the `files` field in `package.json`.

## Writing a CHANGELOG entry

Add your entry to the top of `CHANGELOG.md`, under a new version header if this is a release, or under the current unreleased section if one exists. Use the existing entries as a style guide.

Sub-sections (use only the ones that apply):

- `### Added` - new features
- `### Changed` - changes to existing behavior
- `### Fixed` - bug fixes
- `### Security` - security-related changes

Each bullet starts with a bold label for the feature or module:

```markdown
- **`src/newscan.ts`**: brief description of what was added and why it matters.
```

---

## Opening a pull request

- Branch name: `<type>/<short-description>` - for example, `fix/stripe-pattern` or `feat/new-surface`
- PR description: what changed, why, and how you tested it
- Reviewers will run the validation checklist against your branch before merging - make sure it passes locally first
- Include a CHANGELOG entry in the PR

## AI assistant prompts

If you are using an AI code assistant (Cursor, Windsurf, Claude Code, or similar), the prompts below will help it stay aligned with the project's conventions at each step. Copy and paste the relevant prompt into your editor chat before starting that step.

---

### Orient your assistant to the project

Use this prompt at the start of any session before making changes.

```
You are helping me contribute to @snytch/nextjs, a security scanning tool for Next.js applications.

The project uses:
- TypeScript 5.x in strict mode, ESM only ("type": "module")
- Node.js >= 18
- Vitest for testing
- ESLint + Prettier for linting

Key rules (from CLAUDE.md — follow these exactly):
- All relative imports must use .js extensions, even when importing .ts files
- No `any` type, no `@ts-ignore`, no non-null assertions without a guard
- All exported functions need JSDoc: @param, @returns, @throws
- No process.exit outside src/cli.ts
- Secret values must never appear in full in any output, test fixture, or report — use truncateValue()
- Regex patterns must be reviewed for ReDoS before submission

Before you make any changes, read src/types.ts and CLAUDE.md so you understand the type system and rules.
```

---

### Write or update tests

Use this prompt when adding tests for new or changed code.

```
I'm writing tests for @snytch/nextjs. Follow these conventions:

- Tests live in src/tests/<module>.test.ts
- Use vi.mock for all filesystem and process I/O — never touch the real filesystem
- For each exported function, test:
  - The happy path with realistic input
  - Empty / missing input (return [], never throw)
  - Malformed input (should handle gracefully)
  - Edge cases documented in the function's JSDoc
- Regex pattern tests must include at least 2 inputs that match and 2 that do not
- Do not write trivial tests that only assert what the fixture already sets

Run the tests after you finish with: npm test
```

### Run the validation checklist

Use this prompt when you are ready to verify your changes before opening a PR.

```
Run the full @snytch/nextjs validation checklist in order. Do not skip any step.

1. npm run lint
2. npm run typecheck
3. npm test
4. npm pack --dry-run

For each step:
- If it passes, say so and move to the next step
- If it fails, show me the error and fix it before continuing
- Do not mark the checklist complete until all four steps pass with no errors

Do not suppress lint rules, skip tests, or add @ts-ignore to make steps pass.
```

Use this prompt after your changes are complete and validated.

```

The CHANGELOG follows this format:
- Top-level header: ## [version] — YYYY-MM-DD
- Sub-sections: ### Added, ### Changed, ### Fixed, ### Security
- Each bullet starts with a bold label for the feature or module, e.g.:
  - **`src/newscan.ts`**: brief description of what was added and why

Look at the existing CHANGELOG.md entries for examples of the style.

My changes are: [describe what you changed here]

Write only the new entry block. Do not modify existing entries.
```

### Prepare your PR description

Use this prompt when writing the pull request description on GitHub.

```
Help me write a GitHub pull request description for @snytch/nextjs.

The PR should:
- Start with a one-paragraph summary of what the change does and why
- Include a "Changes" section with bullet points (not a full diff rehash)
- Include a "Testing" section describing what tests were added or updated
- Include a "Checklist" section confirming:
  - [ ] npm run lint passes
  - [ ] npm run typecheck passes
  - [ ] npm test passes
  - [ ] npm pack --dry-run shows only dist/ and README.md
  - [ ] CHANGELOG.md updated
  - [ ] No real secrets or credentials in any test fixture

My changes: [describe your PR here]
```
